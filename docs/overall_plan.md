# BalaBot - overall plan (KB master)

BalaBot is an MIT-licensed, open-source, single-container multi-agent product: one Docker image containing Hermes itself plus two pre-configured agents, the **principal** (runtime ops, system health, agent growth) and the **governor** (the shared OKF decision ledger), with **Jev (J-E-V, by TypeSafe AI)** as a hard, fail-loud dependency. It is based on Grok Bot (xAI's product model) and is built by Ali Farahat's Balacode team, whose earlier KB entries also cover **Kalam**, the Windows-first voice dictation product that shares the same team and vault. The KB decides the whole stack end to end: product facts and pricing (Kalam), team roles and Bot Mode infrastructure, the Agent Computer (one Linux container, per-agent X displays), orgs/secrets/skills with the "interface in chat, value never is" model, session continuity and Jev compaction, the UI/API contracts, launch doctrine, SEO, and strategy. The KB's own usage rules (README.md) say to start at index.md, read frontmatter first, and treat only ratified notes as knowledge; within the bundle, `plans/balabot-remaining-build-plan.md` calls itself the **MASTER SPEC** ("where the code disagrees, the CODE is changed to match the plan"), and the reference docs under `reference/` are the as-built architecture record. Several launch-era and strategy docs (2026-08) are explicitly `draft` and historical relative to the current BalaBot build, and `plans/grokbot-era-validity-review.md` adjudicates which GrokBot-era claims survive. Where any doc's status conflicts with reality, repo `docs/STATUS.md` is the single source of honest status.

## Plans

### agent-computer-linux-vm.md
`active` design record for the Agent Computer. Ali's requirement: "one VM for everyone; each agent has its own workspace inside it; they must be able to control it together." It grounds the model in xAI's own docs (one shared computer per account; screens are "separate work surfaces, not separate security boundaries"; snapshot-based reset) and in the measured hard constraint: `cua-driver` sessions are lifecycle labels, **not displays** - desktop targets bind to `display_id="primary"`, real input is single-pointer, so per-agent concurrent control REQUIRES per-agent X displays, each with its own driver daemon on its own socket. Design: one Docker container (WSL2) with displays `:1` steve, `:2` jim, `:3` oscar, `/workspace/<agent>` each plus `/workspace/shared`; base image `debian:bookworm-slim` + Xvfb + openbox + Chromium (Alpine rejected: musl fights the prebuilt binaries); expected 0.7-1.2 GB. Host capacity is measured (Ryzen 5 7640HS, Docker/WSL2 capped at 14 GiB of 28.8 GiB). Guardrails: never bake credentials into the image; the Windows desktop is no longer the agent computer.

### agent-intervention-flow.md
`approved-for-build` design for how a bot asks a human for help (login, captcha, 2FA). The decision (Ali, 2026-09-26): "the bot pauses its turn and waits" - it does not park the task and move on. Flow: the bot calls `request_intervention(reason, hint?, url?)` -> SSE frame `event: intervention {bot, reason, hint, resume_token}` -> UI badges the bot's card and focuses its live screen, Ali pinged on Telegram -> Ali takes over THAT bot's display only -> `[Done - resume]` -> `POST /api/intervention/{resume_token}/resolve` -> the paused turn resumes. Rules: take-over is scoped to one bot's display (never another agent's, never `/workspace/shared`, never the host); pause has a timeout resuming with an explicit "unattended" note; no intervention screenshots in logs (captchas are where credentials appear); the bot is told only `{resolved: true, note?}` - never what was typed. Per the log and gap ledger, this flow is designed and approved but **not yet built**.

### balabot-acceptance-scenarios.md
A `test-plan` deriving S1-S10 user-usage scenarios from the spec's own build-order step 8. ### jev-continuity-build-plan.md

Because `bootstrap.py` forces `FORCED_MEMORY_PROVIDER = "holographic"` and only ONE external provider may be registered, the plan wraps rather than replaces: `balabot-jev` composes the holographic provider and forwards its whole delegated surface (`fact_store`, `fact_feedback`). ### org-registry-schema.md

Two deliberately separated stores: the registry at `/opt/data/orgs/registry.json` (orgs, members, resources, grants, fingerprints - safe to read/log/diff) and the secret store at `/opt/data/.secrets/<org>/<NAME>` (0600, raw values only). `scope` is `bot | org`; `access` is `inject | read` with **inject the default and the only ordinary one** (read is refused in code until a real need appears - recommended); revocation sets `revoked_at`, records are never deleted. Secret delivery is Option A (the spec's recommendation): a command helper pointed at `secrets.command.command` that reads the registry, filters by the calling profile's live grants, and prints `KEY=VALUE` lines; Option B (a `SecretSource` plugin) is deferred. Hard rules: no secret value ever in transcript, SSE frame, model context, logs, vault, workspace, or argv; only fingerprints (last 4) displayed; a value that lands in chat is burned and rotated. Open decisions for Ali: confirm first org id `balacode`; accept per-file secret granularity (names leak to volume access, never values); refuse `read` by default.

### org-secrets-and-skills.md
`draft-for-approval` design for the multi-tenant model (Ali, 2026-09-26): an organization owns its own context, skills, env vars/secrets, computer spaces (container `agent-computer-<org>`, manifest `fleet/<org>.json`), and members; cross-org access is a first-class, explicit, revocable grant. It resolves the central tension: the `credential-intake` skill's Rule 1 says never ask for a secret in chat, while Ali wants the entry interface in chat - reconciled as "**The interface is in the chat. The value never is.**" The form is a client-side component POSTing straight to the backend; the value never becomes a message, enters the transcript, or reaches model context; bot tools return `{saved: true, name, fingerprint}`, never the value; bots receive secrets as injected env vars only. Secret injection reuses Hermes (`secrets.sources: [command]`, `secrets.profile_alias: true` = "org secret granted to one bot"); ship Option A now, Option B when the shop grows. Skills have two classes: **learned** (from the self-improvement loop, curated `active -> stale -> archived`, never auto-deleted; surfaced in a Skill Library with pin/promote/archive/view, promotion always a human action) and **brought** (hand-written, skills.sh via `npx skills add`, Hermes hub at agentskills.io - the last always exempt from the curator; third-party skills go quarantine -> review -> promote). ### session-continuity.md
The `plan` (2026-09-26) behind one continuous thread instead of session-per-conversation. It measures the real degradation against the owner's config (`threshold: 0.5`, `target_ratio: 0.2`, `protect_first_n: 3` immortal, `protect_last_n: 20`, `abort_on_summary_failure: false`): an immortal session converges on "the original 3 messages + a stack of summaries + the last 20," and summary failure proceeds silently. Core idea: make compaction lossless by extracting before it runs - a pre-compaction saliency pass classifies dropped content to the governor's OKF ledger (decisions), holographic memory (durable facts), the working set (live task state), or deliberate noise - then "compact freely." The single most important rule: **after compaction, rebuild context from state, not from the previous summary**. Roles: Jev is the selection layer (saliency, context-limit signals); the governor holds the per-session purpose record ("recover its mandate, not just its topic"); the principal watches compaction churn and verifies extraction happened, failing loud. It pressure-tests Ali's front-matter proposal into seven corrections: record topics with spans, index-and-retrieve rather than fold old sessions, three routing outcomes (resume / new+linked / new clean), one Noul per candidate (never a Choice), anchor staleness to events (compaction boundary, session close), pre-filter before Jev, and a confidence gate that asks the user. On the context budget: Ali's 40-70% rule is directionally right but unsafe taken off advertised windows (MECW can fall >99% below advertised; the middle is least-attended); agent transcripts are the densest text, so the budget should sit well below 40% of *effective* context. - **Secrets never in chat/workspace.** "No secret value ever in: transcript, SSE frames, model context, logs, vault, workspace, or argv" (`plans/org-secrets-and-skills.md`, restated in `plans/org-registry-schema.md` and the remaining-build-plan guardrails). The store is "a secrets location (`~/.secrets/` class) - never `workspace/`, never a vault note"; a vault note records only that a secret exists, its name, and its scope. Only fingerprints are displayed; a value that lands in chat anyway is **burned and rotated** (`org-secrets-and-skills.md`, `org-registry-schema.md`, `reference/balabot-architecture.md` key-hygiene note).
- **The interface is in the chat. The value never is.** The in-chat secret form is a client-side component POSTing straight to the backend; the value never becomes a message or reaches model context; bots receive secrets as injected env vars only and can never read the raw value (`plans/org-secrets-and-skills.md`; reconciles the `credential-intake` Rule 1 with Ali's in-chat requirement).
- **Consent before creation.** Bot creation requires human approval - "Nothing is created until a human approves" (`plans/balabot-acceptance-scenarios.md` S7; `plans/grokbot-feature-build-plan.md` P4; `reference/balabot-architecture.md`: peer creation is gated on the user's request). Skill promotion is always a human action (`org-secrets-and-skills.md`); third-party skills land in quarantine, inert, until reviewed (`org-secrets-and-skills.md`, acceptance S4).
- **No fabrication.** "No fabricated data, ever - an endpoint that cannot be real must say so and name the blocker" (`plans/balabot-remaining-build-plan.md` ownership law). The honesty contract: every endpoint returns real data or an explicit `available:false` with a reason; `src/mockData.ts` was deleted; "No endpoint returns fabricated rows, and no control is a permanently-spinning lie" (`reference/balabot-architecture.md`, `balabot-acceptance-scenarios.md` S10). Scoring: PASS only on real command output from the real running product; subagent summaries and unit-test stand-ins do not count; anything that cannot be shown to fail is UNPROVEN (`balabot-acceptance-scenarios.md`, remaining-build-plan Wave 8). Supporting discipline: "Do not re-assert a wave is shipped without a call-site check" (remaining-build-plan audit correction), and the KB's own reading rule that draft/unverified notes are "usable. Do not treat them as Ali-signed" (`README.md`).
- **Org scoping.** "Cross-org grants are explicit, named, revocable; nothing crosses orgs implicitly" (`org-secrets-and-skills.md`, `org-registry-schema.md`, remaining-build-plan guardrails). Fleet separation: the personal Hermes agents are never part of the product fleet and hard-404 on `/api/chat` (`grokbot-feature-build-plan.md` standing rule). Intervention take-over is scoped to exactly the bot that asked - never another agent's display, never the host (`agent-intervention-flow.md`). Never expose the Hermes dashboard; the product surface is the only public app (`grokbot-feature-build-plan.md`, `org-secrets-and-skills.md`, `reference/balabot-architecture.md` domain-cutover section).
- **The user is never overruled.** The hierarchy tops out at USER ("most privilege - approves, overrides, owns the machine"), and the governor is "An authoritative record - but never overrules the user" (`reference/balabot-architecture.md`, `team/principal-and-governor.md`). Secrets and grants are "the user's alone" - explicitly not the principal's remit (`reference/balabot-architecture.md`). Jev classifies but never decides irreversible actions: "Jev proposes; the agent owns the outcome," and a sensor is not a verdict (`reference/balabot-architecture.md`). Ali's deferred-decisions standing instruction - surface parked items rather than deciding unilaterally - is the same rule applied to scope (`plans/deferred-decisions.md`). Editable draft cards with human approval before send are kept as a KEEP item (`grokbot-era-validity-review.md`), and the operating model reserves strategic calls and the desktop repo to Ali (`team/operating-model.md`).
- **Fail loud.** "Fail loudly, never silently degrade" on Jev outage; unreachable Jev is an incident the principal raises (`reference/balabot-architecture.md`, `balabot-acceptance-scenarios.md` S9, `plans/jev-continuity-build-plan.md` non-negotiables). Gates that must fail open (the decision gate; the saliency pass when Jev is down) fail open **with a stated reason recorded** - "bloat is recoverable, a silently dropped decision is not."
